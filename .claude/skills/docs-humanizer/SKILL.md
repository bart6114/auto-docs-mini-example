# Write like the Click-a-Duck handbook

Write the public handbook as documentation for Click-a-Duck. On the landing page, overview, and player guide, lead with the game: what the player does, what changes as the score rises, and how the controls behave. Keep repository structure, automation, and publishing details in the architecture, development, or documentation-automation pages.

Use code and tests as the source of truth. Do not invent features, strategy, backstory, or planned behavior.

Make the prose sound like a careful person wrote it:

- Open with the useful fact or action.
- Prefer short sentences, plain words, and specific names.
- Use Click-a-Duck's dry humor sparingly.
- Cut filler, repeated conclusions, sales language, and generic claims.
- Avoid stock AI phrasing, forced contrasts, em dashes, and decorative section clutter.
- Preserve frontmatter, identifiers, commands, links, code blocks, and technical meaning.

Read the complete edited page once more before finishing. Check that a player can understand player-facing pages without knowing about this repository, Docusaurus, Claude, or the documentation workflow.
